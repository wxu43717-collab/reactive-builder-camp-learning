# 项目方向卡｜多个合约的自动 Gas 补给池

**1. 一句话。** 用户向一个资金池合约（Pool）预存执行费用，并登记多个需要维护的合约。Lasna 上的 Reactive 合约监听 Cron 事件，通过回调触发目标链上的批量检查，资金不足时按规则补充费用，资金充足时跳过，每个对象和整个资金池都有补款预算上限。

**2. 赛道。** Track 2 · Set It and Forget It（个人自动化）。

**3. 目标用户和场景。** 维护多个链上自动化任务的个人开发者，需要逐个查看合约的余额、预付额度和欠款，再手动充值，否则任务可能因费用不足停止执行。本项目用一个预存资金池统一维护多个指定合约，自动判断是否需要补款，记录补款对象、金额、原因及剩余预算。用户可在原合约上调整对象和规则。

这里的“补 Gas”指补充用于支付执行费用的原生币或协议预付额度。首版支持 Sepolia 上的 Reactive Callback 合约，检查它们在已配置 Callback Proxy 中的预付额度（reserves）和欠款（debt），并展示合约自身余额。普通合约的交易费用通常由交易发起者支付，直接给普通合约转 ETH 并不自动替调用者付费，因此后续扩展需要逐类定义检查和充值方式。

资金来自用户预存的 Sepolia ETH。Pool 通过 Callback Proxy 的 `depositTo()` 为指定对象充值，先清偿欠款，再补充预付额度。Pool 的业务补款预算与自动化自身的执行资金分别核算，Lasna 侧还需预备 lREACT。仅在完整清偿欠款后，才把该对象标记为已解除欠费状态。

**4. 第二周最小 Demo。** 一个用户、一个 Sepolia 资金池、三个 Sepolia Callback 合约对象，以及一个 Lasna Reactive 调度合约。首版每批最多检查十个已登记对象。

1. 用户向 Pool 预存 Sepolia ETH，登记三个对象，为它们设置最低预付额度、目标额度、单次补款上限、累计补款上限及补款冷却时间，同时设置 Pool 总预算和本轮检查次数上限。演示覆盖预付额度不足、额度充足和存在欠款三种状态。
2. Lasna 的 Cron 触发带 `onlySystem` 的 `react()`，通过 `requestCallbackV_1_0` 请求一次 Sepolia 批量检查。Pool 继承 `AbstractCallback`，回调首参数为 `address`，同时使用 `onlyServiceProvider` 和 `onlyCallbackSender` 验证来源。
3. Pool 在目标链查询即时费用状态。低于阈值或存在欠款的对象按规则补款，额度充足的对象跳过。补款金额受单次上限、对象剩余预算、Pool 剩余预算和可用资金约束。一个对象充值失败时记录失败并继续处理其他对象，禁止无限重试。
4. 再触发一次检查，验证已补足对象跳过、同一请求不会重复付款，并核验欠款对象的状态。预算耗尽、Pool 可用资金不足或用户暂停时停止补款并记录原因。Lasna 达到预设检查次数后自动退订，避免无限产生检查费用。Pool 停止补款到 Lasna 退订之间仍可能产生检查费用，演示须如实记录。
5. 演示调整规则后重新运行，保留相同合约地址。Pool 和调度合约通过轮次及请求编号关联，Pool 拒绝旧轮次回调。重新运行时先确认目标链配置，再恢复 Lasna 调度，并核验两边轮次一致。
6. 提交 Pool、调度合约及三个对象地址，至少两次批量检查的 Reactive 和回调交易证据，以及补款、跳过和预算耗尽记录。分别列出补款本金、Lasna 执行费用、Sepolia 回调费用和配置交易费用。比较逐个补款与批量补款的实际成本，节省幅度以实测为准。

**5. 团队。** 单人开发，使用 AI 辅助。沿用已验证的 Omni 定时订阅、回调鉴权和退订流程，实现批量费用检查、受限补款、失败隔离、请求去重、预算控制及记录查询。先用 Foundry 测试和区块浏览器完成完整演示。仅 Pool 所有者可管理对象、修改规则、暂停及提取未使用资金。
