## 学习过程

一开始从 Reactive 官网进入 Ecosystem，查看了几个生态项目，最后选择了 Rogues Studio。

最初阅读的是 Reactive 与 Rogues Studio 的合作介绍，但发现文章偏向宣传，基本没有解释具体的技术原理。

于是转向技术博客和 GitHub 源码，找到 Streak System 的具体实现。

这个项目涉及四个合约：

- `StreakSystem`：记录签到状态，判断奖励资格。
- `StreakSystemReactive`：监听 `EarnedNFT` 事件，触发回调。
- `MintNFTCallback`：接收回调，调用铸造合约。
- `RoguesItems`：实际铸造 NFT。

刚开始理解这些概念比较困难，尤其分不清 Reactive 究竟是技术、智能合约，还是一条独立的区块链。

后来尝试把 Reactive 与之前接触过的 Flask、Kafka 等技术联系起来，从软件工程的角度理解它的作用。

进一步弄清了事件驱动的逻辑：

**源链产生事件 → Reactive 监听并处理 → 目标链执行操作。**

研究中还发现，同一个项目的测试网和主网部署并不完全相同。测试网示例涉及 Reactive Kopli 和 Ethereum Sepolia 两条链，而主网示例中的四个合约都部署在 Reactive Mainnet。

因此，Reactive 不仅可以用于跨链通信，也能用于同一条链上的事件驱动自动化。

## 今天使用的方法

今天没有直接让 AI 生成任务答案，而是采用了一套逐步理解的方法：

1. **先寻找原始资料**：从生态官网进入项目，再找到技术博客和 GitHub 源码。
2. **先理解业务，再理解技术**：从玩家签到、获得奖励资格、铸造 NFT 这一业务流程入手，而不是一开始就研究 Solidity。
3. **利用已有知识建立联系**：把 Reactive 与 Kafka 的事件驱动机制进行类比，理解它在架构中的位置。
4. **通过问答检验理解**：让 AI 整理资料、讲解概念，然后自己回答任务的四个问题，再纠正技术名词和逻辑错误。
5. **反过来质疑技术方案**：不只研究 Reactive 怎么实现，还考虑为什么需要它，有没有更简单的替代方案。

整个过程主要是 AI 辅助检索、讲解和检查，我负责理解和提出自己的判断。最后根据自己的回答整理成 Markdown，而不是直接使用 AI 生成的完整技术报告。

## 一些思考

今天最大的疑问是：

**为什么一定要通过 Reactive 才能发放 NFT？**

如果签到系统和 NFT 合约都在同一条链上，完全可以直接调用铸造函数。

如果位于不同链上，也可以用 Python 编写链下监听程序，通过 RPC 获取事件，再向目标链发送交易。

所以 Reactive 并不是让这件事情从不可能变成可能，而是提供了一种不同的自动化架构，减少开发者自行维护监听服务的工作，同时支持跨链交互。

但这也意味着额外的 Gas、回调费用和系统复杂度。具体是否值得使用，还取决于应用需求。
